# 데이터 구축 시스템

지침서 PDF에서 깨져 나오던 글자를 고쳐 데이터를 다시 만드는 곳.
이 폴더는 프로젝트를 맡은 사람만 다룬다. 평소 조회에는 쓰지 않는다.

> **이 저장소에서 바로 실행되지는 않는다.** 스크립트가 저장소 밖의
> 작업 폴더를 전제로 한다 — 원본 PDF(`시설물의 안전 및 유지관리 세부지침.pdf/`)와
> 00~05단계 추출 스크립트(`DB/스크립트/`)는 저장소에 들어 있지 않다.
> 여기 담은 것은 **무엇을 어떻게 고쳤는지에 대한 기록과 재현 근거**이고,
> 그중 `글리프사전.json`은 판본이 바뀌어도 계속 쓰는 자산이다.
> 산출된 데이터 자체는 `data/파생/` 에 들어가 있다.

---

## 무엇이 깨져 있었나

지침서 PDF의 수식은 한컴 수식편집기 폰트(`HyhwpEQ`, `HancomEQN`)로 찍혀 있는데,
이 폰트에는 **ToUnicode CMap이 없다**. 글리프 번호를 실제 글자로 옮겨 주는
번역표가 PDF 안에 들어 있지 않다는 뜻이다. 그래서 pdfplumber는 글자를 못 읽고
글리프 번호(`U+E000`~`U+F8FF`)를 그대로 돌려준다.

거기에 문제가 하나 더 겹친다. 분수는 종이 위에서 위아래로 쌓여 있는데
`extract_text()`는 y좌표로 줄을 갈라 위에서 아래로 이어붙인다. 그래서
`½c′` 한 덩어리가 `1` … `c′` … `―` … `2` 로 흩어진다.

**[표 1.11의2] 콘크리트 바닥판 상세조사 상태평가기준 (2026, 31면)**

| | |
|---|---|
| 원문 | `◦ c′ ≤ 열화깊이 < ½h` |
| 고치기 전 | `◦ 〈E0E7〉′ ≤ 열화깊이 < 〈E0EC〉` (앞뒤에 `〈E034〉` `〈E06D〉` `〈E035〉`가 흩어짐) |
| 고친 뒤 | `◦ c′ ≤ 열화깊이 < ½h` |

이 깨짐은 지침서 전체에서 **43종 · 979회** 나온다 (PDF 4개 합계).

## 어떻게 고쳤나

### 1. 글리프사전.json — 43종을 눈으로 확인해 만든 번역표

각 글리프가 실제로 인쇄된 자리를 PDF에서 잘라내 확대 렌더한 뒤 육안으로 대조했다.
근거 그림은 `보고/글리프_시트_1~4.png`, `보고/글리프_단독확인.png`에 있다.

확인해 보니 배열에 규칙이 있었다.

| 구간 | 뜻 |
|---|---|
| `E000`~`E019` | 이탤릭 대문자 `A`~`Z` |
| `E034`~`E03D` | 숫자 `1 2 3 4 5 6 7 8 9 0` (0이 마지막) |
| `E0E5`~`E0FE` | 이탤릭 소문자 `a`~`z` |
| 개별 | `E042`=`%` `E044`=`(` `E045`=`)` `E046`=`−` `E047`=`=` `E048`=`+` `E052`=`,` `E053`=`.` `E067`=`∑` `E090`=`M` `E09F`=`γ` `E0B1`=`φ` `F09F`=`●` |
| `E06D` | **분수 가로줄** (글자가 아니라 구조) |

사전의 각 항목에는 `확인`(그림으로 직접 본 것, 43종)과 `추정`(규칙으로 미룬 것,
문서에 안 나오는 코드)이 표시돼 있다. `추정` 값을 실제로 쓰게 되면 실행할 때 경고가 뜬다.

### 2. 수식복원.py — 분수를 도로 접는다

분수 가로줄은 두 형태로 나온다. 글리프 `E06D`, 그리고 얇은 그래픽 선(한글 크기 분수).
둘 다 잡아서, 가로줄의 x범위 안에서 **바로 위 한 줄**을 분자, **바로 아래 한 줄**을
분모로 모아 `분자/분모` 한 덩어리로 접는다. 좁은 분수부터 접기 때문에 겹친 분수도
안쪽부터 자연히 풀린다. 남은 조각은 줄 단위로 묶어 위→아래, 줄 안에서는 x순으로 잇는다.

그래픽 선은 표 괘선·제목 밑줄과 헷갈리기 쉬워 **분수선 모양**을 따로 검사한다.
분수선은 분자·분모 폭에 맞춰 그 가운데에 그어지지만, 괘선은 위아래 글자보다 훨씬
길고 가운데도 안 맞는다.

> 이 검사를 넣기 전, 2024 6면에서 폭 297pt짜리 표 괘선이 `철근콘크리트 거더`와
> `점검부위 손상종류`를 분자·분모로 삼켜 제목 한 줄이 통째로 사라졌다.
> 지금은 걸러진다.

```
균열발생면적          균열길이(L)×0.25
──────── ×100 =  ──────────────── ×100 = %      ← 종이
조사단위면적           A(m)×B(m)

균열발생면적/조사단위면적 ×100= (균열길이(L)×0.25)/(A(m)×B(m))×100 = %    ← 복원
```

### 3. 구축.py — 한 번 실행하면 전부 다시 만들어진다

```bash
python 구축.py
```

기존 `DB/스크립트`의 01~05단계를 그대로 쓰되, 텍스트가 만들어지는 **두 지점**에만
복원을 끼운다.

- `02_표추출.셀글자()` · `00_본문추출._글자()` — 표 한 칸
- `00_본문추출.병합스트림()` — 본문 한 줄

끼우는 조건은 **그 자리에 깨진 글자나 분수가 있을 때뿐**이다. 나머지는 기존 코드가
만든 값을 그대로 쓴다. 그래서 세 판본 437개 파일 중 **413개가 바이트 단위로 동일**하고
24개만 바뀌었다 — 그 24개가 정확히 깨진 글자가 있던 파일들이다.

원본 `DB/`와 `연구_2/`는 읽기만 한다. 결과는 전부 `결과/` 아래에 새로 쓴다.

### 어떤 PDF를 읽는가

판본마다 원본이 다른 곳에 있다. `구축.py`의 `원본PDF` 표가 그걸 지정한다.

| 판본 | 원본 | 판형 |
|---|---|---|
| 2023 · 2024 | `시설물의 안전 및 유지관리 세부지침.pdf/{연도} 교량 관련 법령/01. …교량편.pdf` | 2단 (한 장에 두 쪽) |
| 2026 | `연구_2/data/원본pdf/2026.pdf` | 1단 |

`연구_2/data/원본pdf/`의 **2022~2024 파일은 쓰지 않는다.** 제목·표캡션·면번호가
전부 그림으로 구워진 사본이라(이미지 2,900여 개, 2026은 29개) 절도 표번호도
읽히지 않는다. 아래 "2022는 왜…" 참고.

판형 차이는 손댈 게 없다. `pdfnorm.detect_layout()`이 판본마다 1단/2단을 스스로
가려내고, 글꼴 크기도 2026 기준으로 정규화해 넘긴다. 원래 그렇게 만들어진 코드다.

## 2022는 왜 재생성하지 않았나

**이건 글자 깨짐과 무관한, 원래 있던 문제다.**

2022는 쓸 만한 PDF가 없다. `.hwp`만 있다. 지금 프로젝트 안에 있는 2022.pdf는
`연구_1`·`연구_2` 두 곳에 있지만 **MD5가 같은 한 파일**이고, 그 파일은 이렇다.

| 항목 | 2022.pdf | 2026.pdf |
|---|---|---|
| 표 격자 검출 | 48/68면 ✓ | ✓ |
| 표 칸 글자 | 살아 있음 ✓ | ✓ |
| `[표 1.11]` 캡션 | **0면** ✗ | 35면 |
| 절 제목 | **없음** ✗ | 있음 |
| 면번호 | **없음** ✗ | 76면 |
| 제목용 큰 글꼴(20/15/13pt) | **없음** ✗ | 있음 |

글꼴이 `9.0pt`와 `10.6pt`뿐이다. 제목 크기 글자가 한 자도 없다. 즉 **제목 계열
(장·절·목 제목, 표 캡션, 면번호)이 전부 그림으로 구워져 있고 본문·표 칸 글자만
텍스트로 남았다.** 그래서

- `read_printed_no`가 면번호를 못 읽음 → `02_표추출`이 전 면을 건너뜀
- 절 제목이 그림 → `00_본문추출`이 "시작 위치를 못 찾음"

수정 전 원본 코드로 돌려도 결과가 같다. 표 내용은 뽑히지만 **그게 몇 번 표이고
어느 절에 속하는지 알 방법이 없다.**

그래서 2022는 **재생성 대신 기존 파일의 깨진 자리만 바꿔 끼웠다**(`보정.py`).
기존 파일은 지금 없는 옛 PDF로 만들어져서 깨진 조각이 흩어진 순서가 다르다.
문자열을 그대로 맞댈 수 없으므로 순서에 안 휘둘리는 열쇠로 짝을 찾는다.

```
열쇠 = (그 조각에 든 깨진 글자 코드의 다중집합, 한글 낱말의 다중집합)
```

세 단계로 맞춘다. ①`기준:` 연속 줄을 표 한 칸으로 보고 통째로 →
②줄 하나 또는 줄 안의 수식 구간 → ③그래도 짝이 없으면 글자만 사전대로 바꾼다.

③으로 처리된 줄은 뜻은 읽히지만 수식의 앞뒤 차례가 원문과 다르다(22줄).
`보고/변경내역.md`에 전부 원문째 적어 두었다.

> **2022를 제대로 살리려면** HWP를 다시 PDF로 변환하면 된다.
> `시설물의 안전 및 유지관리 세부지침.pdf/HWP를_PDF로_변환.py`로 되고,
> 한글 프로그램이 필요하다. 2023·2024가 그렇게 만들어진 2단 PDF와 같은 결과가
> 나올 것이다. 변환한 뒤 `구축.py`의 `원본PDF`에 2022를 추가하고
> `판본들`에 넣으면 나머지는 자동으로 돈다.

## 파일

| 파일 | 하는 일 |
|---|---|
| `글리프사전.json` | 깨진 글자 → 실제 글자. **핵심 자산.** 한 번 만들면 계속 쓴다 |
| `수식복원.py` | 글자 치환 + 분수 선형화 |
| `구축.py` | 한 번 실행 → 전 단계 재생성 (2023·2024·2026). 판본별 원본 PDF 위치도 여기 |
| `보정.py` | 기존 파일 자리 보정 (2022 — 재추출이 안 되는 판본) |
| `보고서.py` | `보고/변경내역.md` 생성 |
| `보고/` | 변경내역 + 글리프 육안확인 근거 그림 |
| `작업/` | 중간 산출물 (글리프 출현 위치, 실행 로그, 보정 내역) |

## 다시 돌리는 법

```bash
python 구축.py        # 2023·2024·2026 재생성 → 결과/
```
```bash
python 보정.py        # 2022 보정 → 결과/보정/
```
```bash
python 보고서.py      # 보고/변경내역.md 갱신
```

## 새 판본이 들어오면

사전에 없는 글리프를 만나면 실행할 때 이렇게 뜬다.

```
[!] 사전에 없는 코드: ['E0XX']
```

`작업/글리프_출현.json`에서 그 코드의 출현 위치를 찾아 렌더해 확인한 뒤
`글리프사전.json`에 `"상태": "확인"`으로 추가한다. 그 뒤로는 AI 없이 계속 결정론적으로 돈다.
