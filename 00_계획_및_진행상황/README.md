## 1. 무엇을 만드는가

「시설물의 안전 및 유지관리 실시 세부지침(**안전점검·진단 편**) **교량편**」을
현장 점검자가 헷갈리지 않고 쓸 수 있게 하는 소프트웨어.

**화면**(단일 파일 웹 GUI)과 **자유 질문**(MCP 서버) 두 갈래로 낸다. 설치도
서버도 API 키도 필요 없다 — 사용자가 이미 쓰는 AI가 우리 도구를 집어 쓴다.
Claude Code · Gemini CLI · Cursor · VS Code · CLI · 웹 어디서 물어도 같은 답이 나온다.

## 2. 왜 만드는가 — 문제의 정체

처음에는 "지침서가 여기저기 흩어져 있어서 찾기 어렵다"는 문제로 시작했다.
조사해 보니 **더 근본적인 문제**가 있었다.

> **FHWA-RD-01-020 (2001)** — 미국 연방도로청이 25개 주의 현직 교량점검자 **49명**에게
> 같은 교량 7개를 점검시킨 연구.
>
> - 주요 부재 하나당 **평균 4~5개의 서로 다른 등급**이 매겨졌다
> - 평균 ±1점 이내에 든 판정은 **68%뿐**
> - ±2점 이내가 95%

**같은 교량, 같은 부재, 같은 지침서를 보고도 사람마다 등급이 갈린다.**
지침서를 못 찾아서가 아니라, 찾아서 읽고도 다르게 판정한다.

이것을 학계에서는 **평가자 간 변동성(inter-rater variability)** 이라고 부른다.
검색을 아무리 잘 만들어도, 챗봇이 아무리 정확히 인용해도 이 층은 건드리지 못한다.

그래서 이 프로젝트의 목표는 "지침서 검색기"가 아니라
**"판정을 일관되게 만드는 도구"** 다.

## 3. 왜 이 방향인가 — 조사 근거

### 3.1 LLM 단독은 불가능하다

**Grounding LLMs in Agency Standards** (engrxiv 7545) — closed-book / RAG / 전체문서 투입을
통제 비교한 연구.

- **closed-book(LLM 단독) 답변의 56~64%가 사실상 오답**
- 전체문서 투입은 RAG보다 5점 척도에서 **0.14점 나은 대신 토큰 35배**

→ LLM에 더 많이 맡기는 방향의 수익률이 낮다.

### 3.2 오프라인 엣지 RAG의 선례

**BridgeGuard** (arXiv 2608.20372) — FHWA 교량점검 컴플라이언스용 완전 오프라인 시스템.
Ollama + Llama 3.1 + Nomic Embed + pgvector. 델라웨어 874개 교량에서 **정확도 99.77%,
인용 정확도 99.79%**.

핵심 기여는 **섹션 인식 청킹** — 청크 무결성 94.2% vs 고정크기 분할 28.4%.
우리 데이터는 이미 KV 블록으로 원자화돼 있어 이 단계를 통과한 상태다.

### 3.3 LLM 밖의 방법들

조사 결과 이 문제에는 **LLM 이전에 수십 년 된 연구 분야**가 있었다.

| 축 | 방법 | 우리 적용 |
|---|---|---|
| 지식 표현 | RASE 마크업 (ICC SMARTcodes) | 정성 기준 247건 분해 |
| | DMN 결정표 (OMG 표준) | `판정규칙.jsonl` 404건이 이미 거의 이 구조 |
| | 온톨로지 / 지식그래프 | 지침서 ↔ 법령 연결 |
| 개정 이력 | Akoma Ntoso point-in-time (OASIS) | 2015~2026 법령 71개 파일 |
| | FRBRoo 조문단위 시간버전 | 표 번호 밀림 |
| 주관성 | 퍼지 추론 | 등급 경계 단절 완화 |
| | 사례기반추론 + 참조 사진 | AASHTO 매뉴얼 2019가 실제로 채택 |
| 인간 오류 | 포카요케 / 강제 기능 | 필수 증빙, 순차 강제 |
| 탐색 | 패싯 검색 / BM25 | LLM 없이 대부분 해결 |

**결론**: 네 가지 통증 중 자유 질문 하나를 빼면 **LLM이 필수인 곳이 없다.**

## 4. 설계 결정과 그 이유

| 결정 | 이유 |
|---|---|
| **LLM이 등급을 판정하지 않는다** | 비용이 아니라 **재현성**. 같은 손상에 항상 같은 등급, 근거는 표 몇 번 몇 면까지 추적 |
| **비용 최적화를 하지 않는다** | 구독 환경에서 쓰므로 한계비용 0. 도구 호출 횟수를 아끼지 않고 **답변 품질**에만 집중 |
| **기존 `표참조:` 규약 유지** | 참조 문자열이 곧 파일명이라 Read/Glob만 쓰는 에이전트가 그대로 따라간다. 좋은 설계다 |
| **정본은 하나** | `data/`(구버전 4개년)와 `DB/`(신버전 2026)는 **같은 PDF를 두 번 다르게 뽑은 것**. 신버전으로 통일 |
| **내용은 한 곳, 어댑터는 얇게** | superpowers 방식. `SKILL.md` 하나에 쓰고 나머지는 한 줄 포인터 |
| **창은 웹 UI가 메인** | 답변이 글이 아니라 **표·트리·배지**다. 터미널로는 4개 연도 비교를 못 그린다 |

| | └ 대응 파일 없음 | 2건 — 2022 `표_균열률 산정 방법-1/-2` 추출 누락 |

| **P8** | 파서 세대 불일치 | `data/` 구버전(4개년) vs `DB/` 신버전(2026만) |

### P1이 하필 위험한 곳에 몰려 있다

깨진 14건 중 8건이 **2026년 신설 5단계 종합등급 산정 절차표**다.
가장 최근에 바뀌었고 계산이 가장 복잡한 부분이다.

```
본문:   표참조: 표_2단계 : 구조형식별 상태평가결과 결정-1     ← 콜론
파일명: 표_2단계  구조형식별 상태평가결과 결정-1.md            ← 공백 두 칸
```

LLM이 이 문단을 읽다가 표를 따라가려 하면 **파일이 없어서 조용히 실패한다.**
에러가 안 뜬다. 넘어가거나 지어낸다.

### P4 상세 — 표 번호가 밀린 이유

2026년판에 `표1.30 월류(여유고 조사)`가 **신설**되면서 뒤가 한 칸씩 밀렸다.

| 표 제목 | 2022 | 2023 | 2024 | 2026 |
|---|---|---|---|---|
| 일반교량 부재별 가중치 | 1.30 | 1.30 | 1.30 | **1.31** |
| 케이블교량 부재별 가중치 | 1.31 | 1.31 | 1.31 | **1.32** |
| 결함도 점수 범위 | 1.32 | 1.32 | 1.32 | **1.33** |
| 구조물의 안전성평가기준 | 1.33 | 1.33 | 1.33 | **1.34** |
| 기초의 안전성능 평가기준 | 1.35 | 1.35 | 1.35 | **1.38** |

**"표1.31"은 2024년엔 케이블교량, 2026년엔 일반교량 가중치다.**

## 8. Phase 1 진행 상황 — 파이프라인 다년도 일반화

**한 것**: `DB/스크립트/`의 신버전 파서(`01_문서골격` → `02_표추출` → `03_검수` →
`04_판정규칙`)를 2022~2024 PDF에도 돌아가도록 일반화했다.

- 연도마다 다른 판형(1-up/2-up, 글꼴 배율)은 `연구_2/bridgekb/pdfnorm.py`가 흡수한다.
  물리 페이지를 논리 페이지로 쪼개고, 글꼴 크기를 2026 기준으로 되돌리고, 하단
  인쇄 면번호("1-27" 같은 장-면 표기, 연도 무관 안정 좌표)를 읽어 붙인다.
- **목차·표지 페이지 판별을 "물리 페이지 번호"가 아니라 "인쇄 면번호가 없음"으로
  바꿨다.** 물리 페이지 번호로 걸렀다면 1-up/2-up마다 값이 달라 연도마다
  하드코딩이 필요했을 것.
- **2026 회귀 검증**: 새 파이프라인으로 2026을 다시 뽑아도 절2 7 / 절3 18 / 목 40 /
  표 75개(자동통과 72) / 판정규칙 404개(정성 247, 61%) — 기존 baseline과 완전히 일치.
- 2022/2023/2024도 전체 파이프라인이 정상 동작. 표 68/65/66개, 판정규칙
  372/370/391개 생성 완료 (`DB/정본/안전점검진단_교량@{연도}/`, `DB/파생/*_판정규칙.jsonl`).

**중요한 정정 — "지표명 오염 9건"은 연도별 데이터 문제가 아니라 파서 버그였다**

원래 계획은 "신버전 파서로 소급 적용하면 오염이 사라진다"였다. 확인해보니 아니었다.
`00_validate.py`의 오염 판정 규칙을 2022~2024 신규 판정규칙에 그대로 적용한 결과:

| 연도 | 지표 전체 | 오염 |
|---|---|---|
| 2022 | 41 | **8** |
| 2023 | 41 | **8** |
| 2024 | 41 | **8** |
| 2026 | 42 | **9** (2026 신설 항목 1개 추가) |

**네 연도 모두 같은 8개 패턴이 그대로 재발한다** (`0㎜미만`, `균열이 주부재 단면의`,
`직접기초(확대기초)에 폭` 등). 즉 이건 연도별 PDF 품질 차이가 아니라
`04_판정규칙.py`의 `지표명()` 함수 자체의 정규식 한계다 — 셀 안에 지표명이 반복되지
않고 컬럼 헤더(`경로`)에만 있는 경우, 정규식이 실패해 원문 앞 16자를 그대로 잘라
쓰는 폴백이 발동한다. 소급 적용으로는 못 고친다. **`지표명()`을 고쳐야 네 연도가
동시에 고쳐진다.**

**해결 — `지표명()` 폴백을 `경로[-1]`로 교체 (2026-09-07)**

값이 지표명 없이 바로 시작하는 셀("30㎜이상" 같은 탄산화 잔여깊이 표)은 정규식이
아예 매칭되지 않아 원문 앞 16자를 그대로 잘라 쓰는 폴백이 발동했다. 지표명은
대개 컬럼 헤더(`경로`)에 이미 있으므로, 폴백을 원문 절단 대신 `경로[-1]`로
바꿨다. 4개 연도 모두 재실행한 결과:

| 연도 | 지표 전체 | 오염(수정 전) | 오염(수정 후) |
|---|---|---|---|
| 2022 | 36 | 8 | **1** |
| 2023 | 36 | 8 | **1** |
| 2024 | 36 | 8 | **1** |
| 2026 | 37 | 9 | **2** |

판정규칙 총 건수·수치/정성 분류는 그대로다(지표 필드만 교체). 남은 것:
- **`균열이 주부재 단면의`**(강 바닥판·거더·교각 부재균열, e등급) — 정규식은
  성공했지만 추출된 텍스트 자체가 "…20% 이상 진전"의 앞부분만 남아 문장으로
  불완전하다. 컬럼 헤더로도 못 고친다(경로가 이미 "부재 균열"이라 더 나을 게
  없음). 원문 자체를 다시 봐야 하는 개별 사례로 남긴다.
- **`온도를 고려한…(신축장`**(교량받침 가동여유량, 2026만) — 이건 지표명 로직
  문제가 아니라 **원본 셀 텍스트 추출 단계의 공백 소실**이다. 원문이
  `"…없음(신축장100 m 미만인 경우)"`로 "신축장"과 "100"이 붙어 나온다.
  단위도 "m"으로 잡혀 있는데 문맥상 "㎜"였을 가능성이 높다(가동 여유량이
  100미터일 리 없음). `02_표추출.py`의 셀 텍스트 추출(`extract_text` 허용오차)
  쪽을 봐야 하는 별개 이슈.
- Phase 0 진단 스크립트(`build/00_validate.py`)의 `POLLUTION_TRUNCATED` 정규식도
  같이 고쳤다. `에\s*폭` 패턴은 "교대와 날개벽사이에 폭", "직접기초(확대기초)에
  폭"처럼 그 자체로 완결된 지표명까지 오탐하고 있었다 — 지표명이 실제로 "폭"으로
  끝나는 게 이 도메인에서는 흔한 정상 패턴이라 신호가 아니었다. 제거했다.

**해결 — 본문 문단 추출 단계 신설 (`DB/스크립트/00_본문추출.py`, 2026-09-07)**

01~05단계는 절 위치와 표만 다루고 문단 텍스트(및 그 안의 `표참조:` 상호참조)는
아예 추출하지 않는다는 걸 발견했다 — 그 기능은 `연구_1/스크립트`의
`추출_전체표.py`에만 있었다(이미 4개 연도 297개 파일로 검증된 로직). 새로
짜지 않고 그 로직을 `DB/스크립트/00_본문추출.py` + `본문공통.py`로 그대로
옮기고 두 가지만 바꿨다: PDF 경로를 `pdfnorm.pdf_path()`로 통일했고, 절
목록을 패턴으로 다시 찾지 않고 `01_문서골격.py`가 만든 `문서.json`의 절2
목록을 그대로 써서 절마다 따로 스크립트를 안 둬도 전체 연도·전체 절을
한 번에 돈다. 출력은 정본이 아니라 파생(`DB/파생/본문/`, `DB/파생/본문표/`)에
둔다 — 사람이 읽는 뷰이지 그 자체가 정본은 아니라서.

**검증**: 4개 연도 × 7개 절 = 28개 본문 파일 중 24개가 구버전(`연구_1/data`)과
**byte-for-byte 완전히 일치**한다. 나머지 4개(연도별 1.7절)는 파일명의
가운뎃점(`·`) 표기 차이로 자동 비교가 매칭을 못했을 뿐, 내용은 확인 결과 동일.

**이식 과정에서 잡은 버그 2개** (둘 다 이번에 새로 발견해서 고침, 옮기기 전
로직에는 없던 문제 - `pdfnorm` 좌표계에 맞추다 생긴 것):

1. **글꼴 크기 배율 방향이 반대로 들어감.** `pdfnorm.Layout.scale`은 2-up의
   축소된 크기를 "곱해서" 2026 기준으로 끌어올리는 배율(예 1.415)인데,
   옛 스크립트의 `cfg["scale"]`은 반대로 2026 기준값을 "낮춰서" 원본과
   맞추는 배율(0.71)이었다. 그대로 옮기면서 값만 pdfnorm 것을 넣어
   방향이 뒤집혔다 — 2023·2024(2-up 연도) 전체가 아무 절도 못 찾고 실패.
2. **2024년 PDF의 마지막 물리면만 판형이 다르다**(다른 면은 가로 841×595
   2-up인데 마지막 면만 세로 595×841 단면). 이 면은 하단에 인쇄 면번호가
   없는데, `01_문서골격.py`·`02_표추출.py`가 쓰던 "인쇄면 없으면 표지·목차로
   보고 건너뛴다" 규칙이 이 면도 표지로 오판해 **2024년 마지막 절(1.7
   보수·보강 방법)이 통째로 사라져 있었다.** "인쇄면이 없으면 건너뛴다"를
   "**첫 인쇄면을 보기 전까지만** 건너뛴다"로 바꿔 고쳤다 — 선두 표지·목차만
   건너뛰고, 이후에 나오는 면은 인쇄면이 없어도 포함한다.

2026 회귀는 이 수정 후에도 그대로 유지된다(절2 7 / 표 75개/자동통과 72,
17개 테스트 통과).

**해결 — `표참조:` 깨진 링크 12건 자동 수복 (2026-09-07)**

`DB/파생/본문(표)/`에 대해 링크 무결성을 다시 재본 결과 baseline과 정확히 같은
14/271건(5.2%)이 재현됐다(포팅이 새 문제를 만들지 않았다는 뜻이기도 하다).
원인은 표 제목에 콜론이 있을 때(`"2단계 : 구조형식별..."`) 파일명 생성
함수(`파일명_무번호`)는 콜론을 지우는데 `표참조:` 줄은 원문을 그대로 써서
둘이 어긋난 것 — 참조 문자열도 파일명과 똑같이 정리하도록 고쳤다.
**결과: 14건 → 2건.** 남은 2건(2022년 `표_균열률 산정 방법-1/-2`)은 표기
문제가 아니라 §9에 있는 실제 추출 누락 — PDF 안에서 격자 표가 아니라
도식(그림) 형태로 그려져 있어 `find_tables()`가 못 잡는다. 원본을 다시 봐야
하는 별개 사안으로 남긴다.

**남은 다음 단계 후보**
1. 동의어 3쌍은 개념 사전(Phase 2)으로 넘김
2. 2022 `표_균열률 산정 방법-1/-2` 도식형 표 — 원본 PDF 재확인 필요(위 항목)
3. `config.py`의 `DATA_DIR`을 구버전(`연구_1/data`)에서 신버전(`DB/파생/본문`,
   `DB/파생/본문표`)으로 전환 — "정본은 하나" 원칙의 실제 이행. `anchor` 도구
   등 조회 계층이 이 경로를 읽도록 바뀌어야 함
4. 교량받침 가동여유량 단위/공백 소실 건 — `02_표추출.py` 셀 텍스트 추출
   허용오차 조정
5. 절 제목의 가운뎃점(·) 소실 (예: "보수·보강"→"보수 보강") — `01_문서골격.py`가
   쓰는 `공통.py`의 줄묶기 문자 결합 로직 점검
